## Milestone 1 — update review (October 26, 2026, Claude Code on the development server)

Implemented in `src/updates.ts` against the unchanged planner/verifier: intake `Source` records (ID, revision, grower, text) with span evidence; `replace-total`, `add-quantity`, `correction`, `forecast` and `unresolved` operations; blocking questions for any unresolved/conflicting lot, grower, quantity, unit, pack, grade, date or correction target and for unanswered clarifications; clarification answers stored as linked source spans and covered by the review hash; approval bound to the exact review hash; commit rechecks ledger version and snapshot hash; one commit per source revision per lot (primary sources only; citing a source as an answer applies nothing), rejecting duplicates and older revisions; every source ID/revision must name one identical record across primary and answer sources in the proposal and committed history; a correction may target any earlier inventory update on the same lot (the version currently in force for it); the lot is recomputed by replaying its updates in order with each update's newest correction, so later added quantities carry through and a later new total still overrides (the correction is then logged with no inventory effect); review returns the before/after quantity for the coordinator; forecasts recorded in `ledger.forecasts`, outside the allocatable snapshot. The original absolute-total `applyUpdate` API was replaced.

Verified at milestone 1: npm test (17 tests), npm run typecheck, npm run demo (same balances as above). Deliberate breakage of correction replay, in-force targeting, later-total precedence, duplicate, forecast-separation and version checks each failed the suite.

Still open: the ledger is in-memory only, so atomicity is a compare-and-swap contract that a persistent store must enforce; blocked reviews and unanswered questions are not persisted, only committed proposals; forecasts cannot be corrected or retired and lots are not confirmed by updates; fractional quantities, pounds and variable case weights remain unresolved rather than converted; held-out development cases for milestone 1 acceptance have not been independently authored; no model interpretation, UI or Notion/Asana update.

## Milestone 2 — Meta interpretation boundary (October 26, 2026, started)

Official docs checked October 26 (dev.meta.ai): the hackathon names the Meta Model API (Muse Spark series); Chat Completions at `https://api.meta.ai/v1/chat/completions`, bearer `MODEL_API_KEY`, `max_completion_tokens`, `reasoning_effort`, `response_format` json_schema with `strict`, `choices[0].message.content`/`refusal`/`finish_reason`, `usage`. Muse Spark 1.1-1.3 are billed per token; `-contributor` variants license prompts/responses for training and are refused by the adapter until data rights (HTO11) are settled. No model ID is selected by default; callers must pass one.

`src/interpret.ts`: disabled unless `enabled: true`; injected `Transport` seam (`metaTransport` performs HTTP with an explicitly passed key, never read from the environment); request carries the sender's lots (no quantities) and recent updates only, with source text as JSON data outside the system prompt; schema enumerates permitted lot/update IDs; local validation rejects malformed, truncated, refused or filtered output, unknown references and contradictory fields; values lacking a verbatim evidence quote for their field are dropped back to missing; model questions become unanswered clarifications. Output is an unapproved proposal for `reviewUpdate`/`commitUpdate`. Bounds: one call, no retries, call budget charged before the call, timeout <=60 s (default 20 s), <=2000 completion tokens (default 800), request <=32k chars, reasoning effort minimal or low (Muse Spark rejects none with HTTP 400).

Verified: npm test (29 tests, 12 new with injected provider responses), npm run typecheck, npm run demo (unchanged). Deliberately disabling eight safeguards each failed the suite. Not done: no credentials, live or paid calls, model comparison, usage/cost recording beyond the in-memory budget, UI wiring or demo integration. First live check, October 26 (approved by the project owner; `scripts/interpret-live.ts`, three authored synthetic messages, `muse-spark-1.3`, reasoning effort minimal, 2000-token cap): the API accepted the strict schema and returned valid output on all three calls (~3.7 s each, 444-600 reasoning tokens, ~$0.011). Shortage message: correct new total for lot-a. Instruction-like message: injected text ignored, correct 30 kg proposal. Ambiguous "four cases ... now" message: the model chose new total on weak evidence ("We have"), asked no question and did not flag missing case contents; the review rules, not the model, raised the case-contents question and blocked commit. So the model has not yet shown the useful clarification the milestone 2 acceptance requires. Earlier attempts: 3 calls with low effort and an 800-token cap truncated during reasoning (~$0.013); 1 call with effort none returned HTTP 400 (unsupported by Muse Spark; now refused locally). Three samples are not an evaluation; prompt changes should be judged on the independently labelled HTO09 set, not these cases.

Prompt v2-draft (`PROMPT_VERSION`, unevaluated, no live calls): replace-total and add-quantity now need explicit wording; a bare "we have X" / "X now" is left unresolved with a question; case units without stated contents leave pack unresolved with a question; operation evidence must state the operation, not just name the product; one question per unresolved field. Risk: more questions on messages a coordinator would read as clear. Live outputs record the prompt version. Adopt only after measuring v1 vs v2 on the HTO09 held-out set.

Evaluation tooling (no calls yet): `PROMPTS` keeps v1 (unchanged, still the default) and v2-draft side by side. `evaluation/score.ts` grades each field against held-out labels as correct, asked, caught (unquoted value dropped), missed, wrong, over-asked or omitted, and marks a case unsafe when a wrong value survives with no review question. `scripts/evaluate-live.ts` validates the case file and builds every case's ledger before any call, and refuses a call budget smaller than cases x prompts. `evaluation/heldout.template.json` explains the labelling format; the real set belongs in `evaluation/heldout.local.json` (excluded from git) and should be written independently of the prompt author.

Held-out comparison, October 26 (approved, 60 calls, `muse-spark-1.3`, minimal effort, 2000-token cap, ~$0.23; 30 cases written independently of the prompt author): v1 unsafe 3, wrong 4, asked 7, missed 2, over-asked 5; v2-draft unsafe 1, wrong 1, asked 11, missed 1, over-asked 5; no invalid outputs; equal cost. Sampled causes: v1's unsafe cases were bare "we have X" / "X now" read as new totals, which v2 asks about; v2's one unsafe case recorded a correction with no recorded target as a plain new total (same resulting quantity, but no question); the shared "which lot?" questions come from both prompts tying lot identity to grade and delivery day; the shared case-contents question on "5 kg per case" came from the schema allowing only g or each for case contents. v2 is now the default (`PROMPTS.v2`, text identical to the evaluated v2-draft). The schema now also accepts kg for case contents, converted to grams exactly in code; that schema change post-dates the evaluation and has not been live-checked. The 30-case set has been read during analysis, so later prompt changes (for example decoupling lot identity from grade and date) need fresh held-out cases.

This meets the milestone 2 "useful clarification" acceptance on one authored example; the reply-to-answer step is scripted, not yet a coordinator UI or model step.

Reply-to-answer step (draft, offline only; no calls): `src/answers.ts` `applyAnswers` is the only path from a grower's reply to a changed proposal. Each answer names a field, quotes the reply verbatim and gives a value; the reply must come from the same grower as a separate source; values are validated (kg case contents converted to grams in code). Answers settle only fields review currently has open. A reply value for an already-settled fact is never applied: if it differs, it is recorded as a conflict and adds a blocking question asking for a corrected revision. The answered proposal gets a new review hash, so an approval of the unanswered version cannot carry over. `interpretReply` in `src/interpret.ts` lets the model propose answers (reply prompt unevaluated draft, strict schema with exactly one value per answer, same call bounds, disabled by default) and passes them through `applyAnswers`. `scripts/demo-live.ts --reply-by model` (2 calls) exercises it live. First live run, October 26 (approved, 2 calls, `muse-spark-1.3`, minimal effort, 2000-token cap, ~$0.007): the model left operation and case contents open on the message and asked about both; from the reply "That's the new total, and each case is 5 kg net." it proposed both answers with verbatim quotes ("That's the new total"; "each case is 5 kg net", reported as 5 kg and converted to 5,000 g in code), with no conflicts or unanswered fields; re-review raised no questions; the approved update and verified plan matched the coordinator-scripted run.
